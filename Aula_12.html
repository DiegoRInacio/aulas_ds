O que é Big Data? Os 3 (ou 5) V's

Fundamentos
V

Volume

TB, PB, EB de dados. Uma rede social gera 500 TB/dia. Um telescópio pode gerar 200 GB/s.

V

Velocidade

Dados chegam em tempo real (streaming). Bolsa de valores: milisegundos. IoT: milhões de sensores/s.

V

Variedade

Estruturado (tabelas), semi-estruturado (JSON, XML), não-estruturado (texto, imagem, vídeo).

+ 2 V's frequentemente citados

  • Veracidade: qualidade e confiabilidade dos dados (garbage in, garbage out)
  • Valor: o objetivo final — transformar dados em decisões de negócio

Quando NÃO usar ferramentas de Big Data

A maioria dos projetos não precisa de Spark ou Hadoop. Use ferramentas simples sempre que possível:

  • Dados < 10 GB → pandas resolve com folga
  • Dados < 100 GB → DuckDB ou polars
  • Dados > 100 GB ou crescendo → considere Spark
  • Streaming em tempo real → Spark Streaming + Kafka
  • Dados distribuídos globalmente → Cloud (BigQuery, Snowflake)

Hadoop Ecosystem & MapReduce

Hadoop Ecosystem

Hadoop

HDFS — Hadoop Distributed File System

O sistema de arquivos distribuído do Hadoop. Divide os arquivos em blocos de 128 MB e os replica em múltiplos servidores (padrão: 3 réplicas).

YARN — Yet Another Resource Negotiator

Gerenciador de recursos do cluster. Decide quantos cores e memória cada aplicação recebe. Permite rodar Spark, Hive e MapReduce no mesmo cluster simultaneamente.

  • ResourceManager: gerencia o cluster todo (como um SO)
  • NodeManager: gerencia recursos de cada nó (como um processo)

Por que distribuir os dados?

Um arquivo de 1 TB não cabe em um único servidor comum. O HDFS resolve isso dividindo em 8.192 blocos de 128 MB e espalhando por centenas de máquinas.


Fault tolerance (tolerância a falhas): se um DataNode cair, o HDFS usa as réplicas dos outros nós automaticamente — sem perda de dados e sem interrupção do processamento.


Data locality (localidade dos dados): o MapReduce move o código até onde os dados estão — não o contrário. Isso evita gargalos de rede.

MapReduce — O Paradigma

MapReduce

Fase MAP — paralelismo total

Cada worker recebe uma partição dos dados e aplica a função map, produzindo pares chave-valor:

# mapper(linha) → [(chave, valor), ...]
"dados são importantes"
  → [("dados",1), ("são",1), ("importantes",1)]

"dados distribuídos"
  → [("dados",1), ("distribuídos",1)]

Fase REDUCE — agregação

Após o shuffle (redistribuição por chave), cada reducer agrega os valores da mesma chave:

# Após shuffle:
"dados" → [1, 1]   # todos os 1s agrupados

# reducer aplica a função de redução:
reduce(lambda a,b: a+b, [1, 1]) = 2
# resultado: ("dados", 2)

Por que o MapReduce é poderoso?

Qualquer problema que possa ser expresso como map + reduce pode ser paralelizado automaticamente em centenas de máquinas, sem que o programador precise gerenciar a distribuição.


Exemplos de problemas mapeados para MapReduce:

  • WordCount: map=tokenizar, reduce=somar
  • Ranking: map=extrair pontos, reduce=ordenar
  • Join de tabelas: map=chave de join, reduce=combinar
  • Médias por grupo: map=extrair valor, reduce=avg
  • PageRank: map=links de saída, reduce=somar pesos

Limitação do Hadoop MapReduce

Cada fase MapReduce escreve resultados intermediários no disco (HDFS). Para pipelines com muitas etapas, isso se torna um gargalo enorme — por isso o Spark nasceu.

Apache Spark — Processamento em Memória

Spark vs Hadoop MapReduce

Spark

A diferença fundamental: disco vs memória

Hadoop MapReduce escreve o resultado de cada etapa no disco (HDFS). Para um pipeline com 10 etapas, são 10 escritas e 10 leituras de disco.


O Spark mantém os dados em memória RAM entre as etapas. Memória é 100× mais rápida que disco.


Hadoop: [Map]→💾→[Reduce]→💾→[Map]→💾→[Reduce]
Spark: [Map]→🧠→[Reduce]→🧠→[Map]→🧠→[Reduce]
Spark ≈ 10–100× mais rápido que Hadoop MapReduce
Especialmente em algoritmos iterativos (ML, grafos)

Arquitetura do Spark

Spark

Driver — o cérebro

O processo onde seu código Python roda. Responsável por:

  • Criar o SparkContext (ponto de entrada)
  • Construir o DAG (plano de execução)
  • Dividir o trabalho em tasks e enviá-las aos executors
  • Coletar os resultados finais (quando necessário)

Executors — os trabalhadores

Processos que rodam nos workers do cluster. Cada executor:

  • Processa as partições de dados atribuídas
  • Mantém dados em cache (memória ou disco)
  • Retorna resultados ao driver
  • Roda em paralelo com outros executors

Cluster Managers suportados

  • Local: todos os processos na mesma máquina — ideal para desenvolvimento
  • YARN: gerenciador do Hadoop — mais comum em clusters on-premise
  • Kubernetes: orquestração de containers — padrão em cloud moderna
  • Standalone: gerenciador próprio do Spark — simples de configurar
  • Databricks / EMR / GCP Dataproc: Spark gerenciado na nuvem (sem configurar cluster)

Modo local — o que usamos nesta aula

spark = SparkSession.builder
  .master("local[*]")  # * = todos os núcleos
  .appName("Aula12")
  .getOrCreate()

No modo local, Driver e Executors rodam no mesmo processo. Perfeito para aprender e testar código.

RDD vs DataFrame vs Dataset

APIs Spark

RDD — Resilient Distributed Dataset

A abstração mais baixa do Spark. Uma coleção distribuída de objetos Python que pode ser processada em paralelo.

  • Sem schema definido — tipagem fraca
  • Sem otimização automática (você define a lógica)
  • Útil para dados não-estruturados
  • API funcional: map(), filter(), reduce()
rdd.flatMap(mapper)
   .reduceByKey(lambda a, b: a + b)
   .sortBy(lambda x: x[1], ascending=False)

DataFrame — a escolha preferida

Como um pandas DataFrame, mas distribuído. Tem schema, é otimizado pelo Catalyst e é muito mais eficiente que RDD.

df.filter(F.col("valor") > 100)
  .groupBy("categoria")
  .agg(F.sum("valor").alias("total"))

Lazy Evaluation — avaliação preguiçosa

Quando você escreve transformações em Spark, elas não executam imediatamente. O Spark constrói um grafo (DAG) de operações e só executa quando você chama uma action.


df2 = df.filter(...) # ← não executa
df3 = df2.groupBy(...) # ← não executa
df3.show() # ← EXECUTA tudo

Transformações (lazy): filter, select, groupBy, join, map, flatMap, withColumn

Actions (eager — executam o DAG): show, count, collect, save, take, write

DAG — Grafo de Execução e Catalyst Optimizer

Otimização

O que é o DAG?

Directed Acyclic Graph — o Spark representa o plano de execução como um grafo onde cada nó é uma transformação e as arestas indicam dependências.

  • Stages: grupos de transformações sem shuffle
  • Tasks: cada stage tem uma task por partição
  • Shuffle boundary: ponto entre stages onde dados são redistribuídos
Stage 1:  parallelize → flatMap → map
               ↓ shuffle boundary ↓
Stage 2:  reduceByKey → sortBy → take(15)

Catalyst Optimizer — o coração do Spark SQL

  1. Plano lógico não resolvido (parsing)
  2. Plano lógico resolvido (schema validation)
  3. Plano lógico otimizado (regras de reescrita)
  4. Plano físico (seleção de algoritmos)
  5. Geração de bytecode JVM otimizado

Otimizações automáticas do Catalyst

  • Predicate pushdown: move filtros o mais próximo possível da fonte — processa menos dados desde o início
  • Column pruning: elimina colunas não usadas antes de processar — reduz I/O
  • Join reordering: reordena joins para processar a tabela menor primeiro
  • Constant folding: avalia expressões constantes em tempo de compilação

Consequência prática: você pode escrever código legível (com operações na ordem natural) e o Catalyst encontra a ordem de execução mais eficiente automaticamente.

# Mostre o plano de execução:
df.filter(...).groupBy(...).explain()
# == Physical Plan ==
# HashAggregate (keys=[...])
# +- Exchange hashpartitioning(...)
#    +- HashAggregate (keys=[...])
#       +- Project [...]
#          +- Filter (valor > 100)
#             +- Scan ...

VectorAssembler — por que é obrigatório?

O MLlib requer que todas as features sejam combinadas em um único vetor (coluna features). O VectorAssembler faz isso:

assembler = VectorAssembler(
    inputCols=["val", "desc", "cat_idx"],
    outputCol="features"
)
# (100.5, 10, 2.0) → DenseVector([100.5, 10.0, 2.0])

Particionamento, Cache e Performance

Otimização

Partições — a unidade de paralelismo

Um DataFrame é dividido em partições. Cada partição é processada por uma task em um executor. O número de partições determina o grau de paralelismo.

  • Poucas partições → subutiliza o cluster
  • Muitas partições → overhead de gerenciamento
  • Regra: 2–4 partições por núcleo do cluster
# Redistribui com full shuffle (caro!)
df.repartition(8)

# Apenas REDUZ partições, sem shuffle (barato)
df.coalesce(2)

Cache — reutilize sem recalcular

df.cache()      # armazena em memória
df.persist()    # idem — aceita StorageLevel
df.unpersist()  # libera quando não precisar mais

# Use quando o mesmo DF é referenciado
# em múltiplas actions (evita recalcular)

Regras práticas de performance

  • Filtre cedo: coloque filtros no início do pipeline — reduz os dados processados nas operações seguintes
  • Selecione apenas as colunas necessárias: select(cols) antes de operações pesadas
  • Evite collect() em grandes datasets: traz todos os dados para o driver — pode causar OOM
  • Use cache() estrategicamente: no ponto onde o DataFrame será reutilizado múltiplas vezes
  • Broadcast joins: quando uma tabela é pequena, use broadcast() para evitar shuffle
  • Evite UDFs Python quando possível: as funções nativas do Spark (F.col, F.when, etc.) são otimizadas e muito mais rápidas

Lakehouse Architecture — o padrão moderno

Combina o melhor de Data Warehouses (SQL, governança) com Data Lakes (escala, custo baixo):

Bronze Layer
Dados brutos, como chegaram. Nenhuma transformação.
Silver Layer
Dados limpos, validados e enriquecidos.
Gold Layer
Dados agregados, prontos para análise e ML.

Guia Prático — Qual Ferramenta Usar?

Decisão
Situação Tamanho dos Dados Ferramenta Recomendada Por quê?
Análise exploratória rápida < 1 GB pandas Simples, rápido, muito suporte
Análise local de dados médios 1–50 GB DuckDB / Polars Mais rápido que pandas, sem cluster
Processamento batch corporativo 50 GB – PB Apache Spark Distribuído, MLlib integrado, SQL
Streaming em tempo real Qualquer Spark + Kafka Latência baixa, microbatch
Data Warehouse na nuvem TB – PB BigQuery / Snowflake Serverless, SQL, escala automática

Arquivo legado Hadoop Qualquer Spark sobre HDFS Compatível com HDFS, 10–100× mais rápido

Regra de ouro

Comece sempre com a ferramenta mais simples. Migre para Spark apenas quando os dados ou a latência exigirem. A complexidade operacional de um cluster Spark é real — só justifica quando os benefícios superam o custo de manutenção.
